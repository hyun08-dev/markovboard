# 개발 일지

커밋 메시지와 함께 **어떤 수학적 판단을 거쳐 현재 모델에 도달했는지**를 남긴다.
완성된 코드만이 아니라 버린 접근과 수정 과정도 기록한다. (계획서 §13)

## Phase 0 — 스캐폴딩

Vite + React + TypeScript + Vitest 로 프로젝트를 세웠다.
계획서 §7의 원칙에 따라 **선형대수와 확률 계산은 전부 직접 구현**하고, 라이브러리는
렌더링(React)과 차트(Recharts)에만 쓴다. 상태가 43개 규모라 브라우저에서 즉시
계산되므로 WebAssembly나 Web Worker는 두지 않는다.

`tsconfig` 에 `noUncheckedIndexedAccess` 를 켰다. 행렬을 배열의 배열로 다루는 코드에서
인덱스 실수를 컴파일 단계에서 잡기 위해서다 (계획서 §7의 TypeScript 채택 이유).

## Phase 1 — 보드·카드 데이터

`board.ts` 는 순수 데이터 배열, `rules.ts`/`transition.ts` 는 효과 함수로 분리했다.
규칙을 데이터에 하드코딩하면 모델 변형 실험마다 코드를 고쳐야 하기 때문이다 (§8).

**발견한 자료 불일치 두 건:**

1. 계획서 §5.1 카드 분류표의 합이 31장으로, 덱 총 장수 30장과 어긋난다.
   이동 카드 13장은 §5.2에 개별 열거되어 있으므로 비이동 카드를 17장으로 맞추었다.
   위치 과정에는 영향이 없다 (12/30 = 40% 불변). → `docs/card-table.md`
2. 베른·베를린·오타와 빌딩료가 자료마다 다르다. 기본 시나리오가 호텔 1채라
   기본 결과에는 영향이 없어 미입력으로 두었다. → `docs/board-table.md`

**막힌 지점:** 나무위키 대조 자료를 자동으로 읽으려 했으나 개발 환경의 네트워크 정책이
namu.wiki 를 차단했다 (egress proxy 403). 우회하지 않고 자료 사본을 직접 전달받았다.

## Phase 1-b — 자료 대조와 데이터 확정

전달받은 문서(「주요 카드」·「게임 방법」·「모노폴리와의 차이점」 사본)를 읽고 대조했다.
**계획서를 그대로 옮기지 않고 원자료와 맞춰 본 것이 이 단계의 핵심이다.**

### 확정한 것

1. **§4.3 불일치 세 건이 모두 문서 B로 확정.** 베른·베를린 빌딩 통행료 55만,
   오타와 60만.
2. **통행료 전체 표 입수.** 대지료 · 별장 1채 · 별장 2채 · 빌딩 · 호텔의 다섯 단계.
   대지료가 만 원 미만(타이베이 2천 원)이라 금액 단위를 만 원 소수로 확장했다.
3. **건축비는 누적하지 않는다.** 부루마불은 건물 종류를 골라 짓는 구조라 호텔만
   지으면 호텔 건축비만 든다. `buildCostMode` 설정은 불필요해져 삭제했다.
   — 미확정 항목 B1 해소.
4. **우주여행 칸은 더블과 무관하게 턴을 끝낸다.** 전이행렬의 더블 재귀를 끊는
   조건이므로 `spaceEndsTurn` 설정으로 남겼다.

### 계획서를 바로잡은 것

**우주여행 초대권은 대형판에서 1장이다.** 자료가 "퀸 엘리자베스 호가 있는 버전에서는
1장, 없는 버전에서는 2장이며 대신 유람선이 없다"고 명시한다. 계획서 §5.2는 우주여행
2장과 유람선 1장을 함께 실어 **두 버전을 섞었다.**

이를 바로잡자 계획서 §5.1 분류표의 합계 불일치(13+7+6+5 = 31 ≠ 30)가 저절로 풀렸다.
이동이 12장이면 정확히 30장이 된다. 두 오류가 같은 원인에서 나온 것이었다.

결과로 **위치 변경 카드가 12장이 아니라 11장**이 되어

$$P(\text{황금열쇠에서 위치 변경}) = 11/30 \approx 36.67\%$$

계획서의 40%는 잘못된 값이다. 이 차이는 실험 8(무인도·서울 유입 경로 분해)에
직접 들어간다.

### 검증을 자료 본문과 맞물리게 했다

표를 옮길 때 가장 위험한 것은 조용한 오타다. 그래서 자료 **본문의 서술값**을 테스트로
박아 두었다.

- "타이베이 풀하우스 37만" → `tollOf(타이베이, 'full') === 3 + 9 + 25`
- "뉴욕 풀하우스 반액대매출 117만 5천" → `investmentOf(뉴욕, 'full') / 2 === 117.5`

표의 숫자를 하나라도 잘못 옮기면 이 두 테스트가 깨진다. 표와 본문이라는 **서로 다른
경로의 두 값이 맞물리는지**를 확인하는 장치다.

### 근사로 남긴 것

'무인도 탈출권(무전기)'은 엄밀히는 무인도 대기 턴을 줄인다. 소지 여부를 상태에 넣으면
상태공간이 두 배가 되므로 넣지 않았다. 한계로 기록한다.

## Phase 2 — 4상태 축소 모델 교차 검증

큰 모델에서 답이 틀리면 **어디가 틀렸는지 알 수 없다.** 그래서 손으로 풀 수 있는
크기의 보드를 먼저 만들었다.

장난감 보드를 아무렇게나 고르지 않았다. 4칸 순환 보드에 주사위만 굴리면 $P$ 가
이중확률행렬이 되어 $\pi$ 가 균등분포로 나오는데, 그러면 **틀린 구현도 통과한다.**
그래서 "3번에 착지하면 1번으로 끌려간다"는 강제 이동을 하나 넣었다. 그 결과

- $\pi$ 가 $(1/6,\ 1/2,\ 1/3)$ 로 **비균등**해져 구현 오류가 드러나고,
- 3번이 **도달 불가능 상태**가 되어 BFS 가지치기의 최소 예제가 되며,
- 특성다항식이 $-\lambda(\lambda-1)(\lambda+1/2)$ 로 깔끔히 인수분해되어
  $|\lambda_2| = 1/2$ 을 손으로 구할 수 있다.

세 성질을 동시에 만족하는 보드를 고른 것이 이 단계에서 한 유일한 설계 판단이다.

검증은 네 경로로 했다. 손계산(유리수 정확 연산) · NumPy 고유벡터 · NumPy 멱승법 ·
몬테카를로 재귀시간. 넷이 모두 일치했고, 오차 감쇠율이 12스텝 내내 0.500000 으로
관측되어 $|\lambda_2|=1/2$ 예측과 맞았다.

**Phase 2 완료 조건(손계산 = NumPy) 충족.** TypeScript 대조는 멱승법이 나오는
Phase 5로 미룬다 — `toy.ts` 에 규칙과 정답을 미리 박아 두었다.

## Phase 3 — 상태공간 확정

43상태를 구현하고 BFS 도달성 검사를 붙였다. 채택안과 버린 안 다섯 가지를
`docs/state-design.md` 에 나란히 적었다.

이 단계에서 한 판단 중 기록할 만한 것 둘.

**기약성은 양방향으로 검사한다.** 정방향 BFS만 돌리면 "출발점에서 모든 상태에 갈 수
있다"만 확인되고 "모든 상태에서 돌아올 수 있다"는 확인되지 않는다. 전이 방향을 뒤집은
그래프에서도 전부 도달 가능해야 강연결이다. 4상태 모델로 이 차이를 테스트했다 —
가지치기 전 행렬은 정방향으로는 3번을 제외한 전부에 닿지만 기약이 아니다.

**우주여행 대기 상태를 만들려다 그만두었다.** 자료에 "우주여행 칸에 도착하면 다음
턴에 이동한다"고 되어 있어 처음에는 상태를 하나 추가할 생각이었다. 그런데 스텝이
턴 단위이므로 "30번에서 턴을 시작한다"는 기존 상태 `c30` 이 이미 그 상황을 정확히
표현한다. 스텝 단위를 턴으로 잡은 결정이 여기서 한 번 더 값을 했다.

## Phase 4 — 전이행렬 생성기

`board.ts`(데이터) → `rules.ts`(칸 효과) → `transition.ts`(턴 전개)로 나눴다.

### 재귀를 버리고 레벨 단위 집계로 바꾼 일

처음에는 더블 재굴림을 그대로 재귀로 짰다. 테스트가 끝나지 않았다.
분기 수를 세어 보니 원인이 분명했다 — 한 번 굴릴 때마다 (주사위 결과 21가지 ×
황금열쇠 카드 30장)이 곱해지고, 더블이면 그 아래로 또 곱해진다. 깊이 3에서 이미
2천만 갈래다.

고친 방법은 **"지금 굴리고 있는 확률질량"을 칸별로 모아 한 레벨씩 밀어내는 것**이다.
같은 칸에 도착한 경로들은 이후 전개가 완전히 같으므로 합쳐도 된다. 깊이당 비용이
40 × 21 × 30 으로 일정해지고 결과는 정확히 같다. 43개 행 전체가 0.1초 안에 나온다.

마르코프 성질(과거를 잊는다)이 계산 구조에 그대로 드러난 지점이다.

### π 와 v 를 한 번에 모으는 이유

한 턴을 전개하면서 전이확률 · 착지 횟수 · 출발선 통과 횟수 · 굴림 수를 함께 모은다.
착지 벡터 $v$ 는 Phase 6의 일이지만, 규칙 전개 코드를 두 벌 두면 반드시 어긋난다.
$\pi$ 와 $v$ 는 **같은 전개에서 나오는 다른 집계**다.

### 테스트가 잡아낸 것 — 두 번 다 테스트가 틀렸다

두 테스트가 실패했는데 둘 다 **내 기댓값이 틀렸고 모델이 맞았다.** 기록해 둔다.

1. `J₀` 의 기대 굴림 수를 1.2 로 적었는데 1.1907 이 나왔다. 순수 순환 보드에서만
   $E[K] = 6/5$ 이고, 실제 보드에서는 무인도나 우주여행에 걸리면 **더블이어도 턴이
   거기서 끝나기** 때문에 그보다 작다. 이 간극이 곧 특수 칸의 효과다.
2. 균등 정책에서 우주여행 칸으로 돌아올 확률을 0으로 적었는데 0.005128 이 나왔다.
   정책이 30번을 목적지에서 제외해도, **황금열쇠 6칸 중 하나에 내린 뒤 우주여행
   초대권(1/30)을 뽑으면** 돌아온다. $6 \times \frac{1}{39} \times \frac{1}{30}
   = 0.005128$ 과 정확히 일치했다.

두 번째는 테스트로 남겼다. 카드 연쇄가 제대로 도는지 확인하는 장치가 된다.

### 해석적 정답 테스트 (§11.2)

특수 칸을 모두 끈 순수 순환 40칸 보드에서 다음을 확인한다.

- $P$ 가 **순환행렬**이다 — 모든 행이 첫 행을 한 칸씩 민 것과 같다
- **열 합도 1**이다 → 이중확률행렬 → $\pi_i = 1/40$ 이 정확히 성립
- $\sum_i v_i = E[K] = 1.2$, 한 턴 기대 이동 거리 $1.2 \times 7 = 8.4$칸
- 턴당 출발선 통과 기대 횟수 $= 8.4/40$

이 테스트 하나가 전이행렬 생성기 버그의 대부분을 잡는다.

### 새로 명시한 가정 A11

"카드로 이동한 뒤 더블 재굴림을 계속하는가"는 규칙서에 없다. 계획서 §3.3의
"더블이면 착지 처리 후 같은 절차를 반복"을 따라 **계속 굴리는 것**으로 정하고
`cardMoveEndsTurn` 플래그로 반대 해석도 실험할 수 있게 남겼다.
